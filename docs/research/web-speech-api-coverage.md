# Cobertura y confiabilidad de la Web Speech API (`SpeechRecognition`) para Bahía

> Investigación de producto — no incluye implementación. Objetivo: decidir si el MVP de Bahía (PWA para talleres mecánicos) puede depender de la Web Speech API nativa del navegador para voz-a-texto, o si necesita un fallback de transcripción externo desde el inicio.
>
> Fecha de la investigación: 2026-07-30/31. Los datos de compatibilidad de navegadores cambian con el tiempo; los números de versión citados aquí reflejan lo que reportaban MDN/caniuse en esa fecha.

## Resumen ejecutivo

La Web Speech API existe y funciona en Chrome/Edge de escritorio y en Chrome para Android, pero **no es confiable como único mecanismo de voz-a-texto para un MVP de producción**: en Chrome (todas las plataformas móviles) el reconocimiento depende de un servicio en la nube de Google y no funciona offline; en Safari/iOS está deliberadamente **deshabilitada cuando la app se instala como PWA en la pantalla de inicio** (justo el modo de uso previsto para Bahía); y el modo `continuous` (dictado prolongado) está roto en Chrome/WebView de Android por diseño. Dado que el taller debe operar con wifi débil/intermitente y la app se instalará como PWA, **se recomienda tratar la Web Speech API como una mejora progresiva opcional (solo en pestaña de navegador, con conexión) y prever desde el diseño un fallback de transcripción server-side (p. ej. Whisper API de OpenAI) o un modelo on-device tipo whisper.cpp/Vosk** para el flujo crítico.

## 2. ¿Requiere conexión a internet?

**Sí, en la inmensa mayoría de los casos reales.** La propia documentación de MDN lo dice explícitamente para Chrome:

> "On some browsers, like Chrome, using Speech Recognition on a web page involves a server-based recognition engine. Your audio is sent to a web service for recognition processing, so it won't work offline."
> — https://developer.mozilla.org/en-US/docs/Web/API/SpeechRecognition

Detalles relevantes encontrados:

- **Chrome (todas las plataformas)**: el motor "clásico" (`webkitSpeechRecognition`, disponible desde v33, el que corre en Android hoy) envía audio a los servidores de Google. Chrome 139+ introdujo métodos experimentales (`SpeechRecognition.available()`, `.install()`, propiedad `processLocally`) para reconocimiento **on-device** con descarga de paquetes de idioma — pero, según MDN BCD, esto **no está implementado en Chrome Android** (`chrome_android.available_static.version_added: false`), solo en Chrome de escritorio, y sigue siendo experimental. Para el objetivo principal de Bahía (móvil/tablet), esta vía offline todavía no existe en producción.
- **Safari / iOS**: Apple no documenta públicamente si `webkitSpeechRecognition` en la web usa el reconocimiento on-device de su framework nativo `SFSpeechRecognizer` (que sí soporta `supportsOnDeviceRecognition` para ciertos idiomas) o si siempre pasa por sus servidores. Un desarrollador probó explícitamente desactivando la conexión a internet antes de iniciar el reconocimiento y reportó fallos, sugiriendo que `requiresOnDeviceRecognition` no se está aplicando de forma consistente desde la API web: issue abierto y sin respuesta de WebKit, "Unclear interimResults Web Speech API implementation in Safari iOS (WebKit)": https://github.com/WebKit/Documentation/issues/120. **Conclusión: no se puede asumir que Safari funcione offline; el comportamiento no está garantizado ni documentado oficialmente por Apple.**
- **Edge**: al compartir motor con Chromium, hereda el mismo modelo server-based que Chrome (cuando efectivamente dispara eventos — ver limitación de la sección 1).
- **Firefox**: no aplica como objetivo, pero de referencia: el soporte sigue detrás de una bandera (`media.webspeech.recognition.enable`) deshabilitada por defecto, no listo para producción (MDN BCD / caniuse).

**Implicación directa para Bahía**: con wifi débil o intermitente en el taller, el reconocimiento de voz nativo puede fallar silenciosamente o devolver error `network` en el peor momento (a media dictado). Cualquier flujo crítico de captura de voz debería degradar con gracia a entrada de texto manual, y no bloquear el flujo de trabajo del mecánico.

## 3. Limitaciones conocidas en producción

- **`continuous` (dictado prolongado) roto en Android**: en Chrome Android, WebView Android y Samsung Internet, la propiedad `continuous` "se puede asignar pero no tiene efecto" (nota oficial en MDN BCD). El origen histórico está documentado en el bug de Chromium [#40324711](https://issues.chromium.org/issues/40324711) (abierto en 2013): los proveedores de reconocimiento de voz de Android no soportaban reconocimiento continuo, y el equipo de Chromium decidió deshabilitar la función por completo en vez de simularla, precisamente para no "mentirle" al desarrollador. Sigue así en 2026. **Para Bahía esto importa porque un mecánico dictando notas con las manos sucias necesita sesiones largas sin tener que pulsar "grabar" después de cada frase** — eso no es posible de forma nativa en Android; hay que reiniciar `start()` manualmente tras cada resultado.
- **PWA instalada vs. pestaña de navegador (iOS)**: como se documentó arriba, WebKit deshabilita expresamente `SpeechRecognition` quitando la vista de `SafariViewController` y en apps añadidas a la pantalla de inicio. Esto es el escenario exacto de una PWA instalada.
- **Fiabilidad de eventos en Edge**: según caniuse, los eventos de la API "no parecen dispararse" en Edge, pese a que el objeto exista (ver sección 1). No verificado de forma independiente en este research; requiere prueba manual.
- **Errores de red / "network error"**: reportes recurrentes en foros de Chromium y del framework Electron/NW.js de que `webkitSpeechRecognition` lanza un error genérico `"network"` cuando el servicio de reconocimiento remoto no está disponible o no puede completarse (hilo de Google Groups: https://groups.google.com/a/chromium.org/g/chromium-html5/c/JJe6KD7-bb8 — foro/no oficial, se cita como evidencia de un patrón recurrente, no como especificación).
- **Timeout de silencio ("no-speech")**: de forma no documentada oficialmente pero ampliamente reportada por desarrolladores, Chrome corta el reconocimiento con un error `no-speech` tras unos pocos segundos sin detectar voz (cifras de ~5 segundos aparecen en discusiones de comunidad). No hay una fuente oficial que fije un número exacto; tratar como comportamiento no garantizado y variable entre versiones/plataformas.
- **Requiere contexto seguro (HTTPS) y servidor**: la nota de MDN BCD sobre Chrome (`webkitSpeechRecognition`, v33+) dice explícitamente: *"You'll need to serve your code through a web server for recognition to work."* Esto es consistente con el requisito general de contexto seguro (HTTPS) que la plataforma web exige para `getUserMedia`/acceso a micrófono. `localhost` funciona para desarrollo; en producción, la PWA de Bahía ya deberá servirse por HTTPS de cualquier forma.
- **Comportamiento inconsistente de eventos en Safari iOS**: según el blog técnico de Andrea Giammarchi (ingeniero conocido por su trabajo en compatibilidad de APIs web; fuente secundaria, no oficial), en Safari móvil solo `start` y `audiostart` se disparan de forma confiable, y los resultados (`result`) llegan con retraso impredecible, lo que obliga a implementar heurísticas propias (p. ej. asumir fin de habla tras ~750ms sin resultados interinos) en vez de depender de los eventos nativos de fin de reconocimiento. La misma fuente reporta que la versión WebView de Safari móvil (usada por apps empaquetadas/algunos flujos de PWA) "lanza un error inmediatamente, sin siquiera pedir activar el micrófono". Fuente: https://webreflection.medium.com/taming-the-web-speech-api-ef64f5a245e1 (blog, no es fuente oficial — se cita explícitamente como tal).
- **Permisos de micrófono**: el usuario debe conceder permiso de micrófono explícitamente; en iOS Safari, además, activar el reconocimiento de voz y la síntesis de voz en la misma interacción de usuario confiable (gesto de clic) es recomendado para evitar diálogos de confirmación adicionales (misma fuente de blog citada arriba).
- **Idiomas y precisión**: no se encontró documentación oficial de Google/Apple sobre tasas de error de reconocimiento específicas por idioma para la Web Speech API (a diferencia de servicios pagos como Google Cloud Speech-to-Text o Whisper, que sí publican benchmarks). Debe asumirse variabilidad no cuantificada, especialmente en español con acentos regionales y vocabulario técnico automotriz (términos que no están en el vocabulario general del reconocedor).

## Conclusión práctica para la decisión de producto

- No usar la Web Speech API como único camino para una función crítica de negocio (p. ej. registrar diagnósticos por voz). Es viable como *mejora progresiva* opcional cuando hay conexión y el usuario está en pestaña de navegador (no en la PWA instalada) — pero incluso ahí, Android tiene el límite de `continuous` y Edge tiene dudas de fiabilidad de eventos sin verificar.
- En iOS, si Bahía se usa como PWA instalada (el modo previsto), la Web Speech API **no va a funcionar en absoluto** según la política actual y deliberada de WebKit — hay que asumir que no existe en ese contexto, no que "puede fallar".
- Si el dictado por voz es un requisito real del producto (no solo "nice to have"), la ruta más robusta para wifi débil es evaluar una opción on-device (whisper.cpp o Vosk, ambas gratuitas y sin dependencia de red en tiempo de ejecución) para el flujo offline, con un fallback server-side (Whisper API de OpenAI u otro proveedor) cuando haya conexión y se necesite mayor precisión. Esta decisión de arquitectura queda fuera del alcance de este research — aquí solo se documenta que las opciones existen.
